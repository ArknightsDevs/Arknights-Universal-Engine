# 0058 Stronghold 的 kit 作为固定版本的脚本 mod 进入对局

- 状态：已采纳
- 日期：2026-10-12
- 来源：规划讨论 Q32, Q35, Q49, Q16；计划 E1（2026-10-12 选定「兼容层加载 kit」，E1g）

## 背景

MVP 阵容的 72 名六星，引擎原生实现能完整覆盖的天赋与技能为 0（E2 的统计：天赋认出 15/154，技能参数全懂 57/216）。2026-10-12 选定用兼容层加载 Stronghold 的 kit（E1）。之前两条决定与此冲突：

- [0041](0041-stronghold-differential-testing.md)：固定版本的 Stronghold 只在开发和测试时使用，作差分对照；
- [0038](0038-script-mod-rewriting.md)：脚本 mod 由服务器在安装时改写导入路径，MVP 之后才做。

本条取代这两条，并重述其中仍然有效的部分。

## 决定

- **对照**（沿用 0041）：以固定版本的 Stronghold 为差分对照。纯函数要与它逐位一致；整场战斗的摘要差异必须登记原因（见 [0043](0043-ci-gates-and-registry.md)）。
- **kit 进入对局**：同一固定版本里的干员 kit 作为一个内置的脚本 mod，在对局中运行（兼容-2…兼容-5）。
  - 服务器安装时从上游取这一固定提交（与对照用的同一个），我们的仓库不收录它的源码。
  - 只启用通过检查的 kit：在小关卡冒烟运行中不报错，并通过逐个 kit 的差分对照（计划 E1h）；名单写在内容里，随版本变化。其余干员用引擎的原生实现。
  - 内容哈希包含固定提交与启用名单；两端不一致时不开局（同步-9）。
- **脚本 mod 的改写**（沿用 0038）：服务器安装 mod 时，用同一张映射表改写导入路径（见 [0010](0010-import-mapping-table.md)），再按内容哈希提供给客户端；浏览器端从不改写。服务器的仲裁在 Node 里用同一张表生成的加载钩子。
- **许可**（沿用 0038）：脚本 mod 必须与 GPL 兼容（见 [0003](0003-licensing.md)）。Stronghold 为 GPL-3.0-or-later，可与引擎（GPL）和平台（AGPL）组合；保留其版权与许可声明，平台列出来源与固定提交。数据 mod 不能带脚本（见 [0039](0039-mod-assets.md)）。
- **时机**：内置的 kit mod 现在就做；第三方脚本 mod 仍在 MVP 之后（与数据 mod 的 mod loader 一起）。
- **过渡**：原生接口（[0055](0055-sdk-prepared-now-built-after-mvp.md)）的实现补齐一名干员，就从启用名单里换掉它的 kit。

## 理由

- 不用 kit，MVP 阵容的天赋和技能要逐个手写，远在 MVP 之外；kit 已按 Stronghold 的规则写全，兼容层让它们原样运行。
- 从上游按固定提交安装、不复制进仓库：来源与版本清楚，许可声明随源码保留，升级只改固定提交。
- 只启用通过检查的 kit：未接好的部分不会在对局里悄悄出错。
- 哈希包含 kit：两端运行同一份内容，确定性不受影响。

## 后果

- 服务器安装多一步：取固定提交，生成改写后的模块。离线环境要预先放好这份源码。
- 每次升级固定版本，要重跑冒烟与差分，更新启用名单和差异登记。
- 两端都要载入 kit：仲裁在 Node 里用加载钩子，客户端后台线程用服务器改写后的模块。
- kit 的状态在闭包里，进不了快照：断线重连与断同步恢复改为从头重放（计划 E1f）。

## 备选方案

- 把 kit 源码复制进我们的仓库：否决，来源与升级都不清楚，也让仓库收录他人的大量代码。
- 全部原生重写后再上线：否决，MVP 阵容要等太久；原生实现仍按干员逐个推进。
- 不经检查全部启用：否决，未接好的 kit 会在对局里出错。
