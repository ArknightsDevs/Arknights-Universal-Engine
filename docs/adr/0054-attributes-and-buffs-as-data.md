# 0054 属性由 Buff 推导，Buff 是纯数据

- 状态：已采纳
- 日期：2026-10-11
- 来源：M2 实施；规划讨论 Q34、Q36、Q40

## 背景

M2 要加入属性、Buff、异常状态、伤害和索敌。几个约束：

- 世界状态必须是纯数据，快照就是它的深拷贝（同步-2），状态哈希逐项覆盖它（同步-1）。
- Stronghold 的 Buff 里有函数（`onTick`、`onExpire`、函数形式的修饰器），持续时间是浮点秒；单位的面板属性缓存在单位上，靠"脏"标记重算。
- 官方规则里，顺序有实际影响：
  - 同名 Buff 按获取顺序排队（PRTS「常见同名状态」）；
  - 伤判效果按「事件优先级＞获取顺序」逐个结算（PRTS「伤判效果」）；
  - Buff 的剩余时间每帧按衰减率减少，抵抗率中途变化也会生效（PRTS「Buff的持续时间衰减率」）。

## 决定

- **属性**：单位只保存基础属性 `base`（字段名沿用 Stronghold，与官方数值范围一一对应）和按获取顺序排列的 `buffs`。
  - 面板属性由 `statsOf(unit)` 按需算出。它是这两者的纯函数，不存进状态。
  - 唯一的例外是最大生命值：它变化时要按比例缩放当前生命（属性-4），所以上一次的最大生命值存在单位上。
- **Buff 是纯数据**。每个 Buff 有：
  - 键、来源单位；
  - 修饰器（键名沿用 Stronghold）、标记；
  - 层数；
  - 剩余帧数（−1 表示无限）、触发间隔；
  - 事件优先级、是否可抵抗。

  行为（周期触发、到期、伤判）按键在代码里的行为表中查找，不放进状态。快照和哈希因此只需要处理数据。
- **同名 Buff 并存，每个键只有一条生效**：
  - 默认生效的是最早获取的那条；
  - 「效果取最高」的状态取最强的那条；
  - 叠层和延长时间的 Buff 合并成一条。
- **持续时间以帧为单位**。每帧减去衰减率，可抵抗状态的衰减率随状态抵抗率变化，所以剩余帧数可以是小数。到 0 或以下时到期。
- **哈希把 −0 当作 0**：快照经过 JSON，JSON 不能表示 −0。如果一个对等端从快照恢复、另一个没有，两边的哈希不能因此不同。

## 理由

- 纯数据的 Buff 可以直接快照和哈希，也没有闭包捕获的隐藏状态。
- 属性按需推导，就没有缓存过期的问题。M2 的单位和 Buff 数量下，重算的开销可以忽略；以后性能分析要求时，再加一个按修订号失效的缓存。这个缓存不属于状态。
- 生效规则、结算顺序、衰减率都按官方实现，见 [0013](0013-rewrite-order-official-semantics.md)。

## 后果

- Stronghold 带函数的 Buff 由兼容层转换成数据和行为表条目（M4）。技能和天赋的行为在 M3 加入行为表。
- 和 Stronghold 不同的地方（同名规则、伤判顺序、抵抗的计算方式等）都登记为已知差异。
- 状态哈希改为遍历单位的全部数据（同步-1 已更新）。
